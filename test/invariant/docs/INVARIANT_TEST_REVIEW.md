# 不变量测试函数目录

不变量测试会连续执行随机操作，并反复检查一些规则是否始终成立，例如“份额总数对得上”“资产没有凭空增加或减少”。本文逐函数说明这些检查，以及用来生成操作、计算预期结果的辅助函数。

共 4 个测试文件，直接定义了 7 个 `invariant_*` 函数和 3 个 `test_*` 确定性测试函数，合计 10 个；继承的函数不重复列出，操作生成器、初始化、收尾和参考算法不算独立测试。混合精度环境另外继承执行 3 个会计不变量，因此 Foundry 实际执行 10 个不变量实例和 3 个确定性测试，共 13 个测试实例。

## 先了解几个名称

- Vault 是资金库；shares 是用户持有的份额；Control 管理角色、暂停和适配器注册；Adapter（适配器）负责连接具体协议。
- Manager 是业务管理人，Guardian 可收紧控制和紧急退出，Keeper 可执行换币迁移；根管理员负责角色管理，不自动拥有这些业务权限。
- V2 的 LP 代币代表流动性权益；V3 的 NFT 代表仓位；IDLE 表示资产直接留在 Vault、不投入池子。低费率和高费率 V3 池分别收取 0.05% 和 0.3% 交易手续费。
- Venue 表示使用哪个池或处于 IDLE；Regime 是策略判断的市场状态；NAV 是按测试价格计算的净资产价值；TWAP 是一段时间内的加权平均价格；Tick 是 V3 的价格位置编号。
- Handler 是测试中的操作生成合约：它选择用户和金额，调用存款、赎回等操作，并检查结果。“独立账本”是测试自己记录的应有份额和资产流入、流出，不直接把 Vault 报出的数值当答案。
- “原生流动性单位”是协议内部记录仓位大小的单位：V2 是 LP 数量，V3 是 liquidity 数值，不等于 Token 数量。“原始单位”是某种 Token 的最小计数单位。
- “状态摘要”是把选定字段汇总成哈希，比较调用前后是否变化；“回滚”是整笔调用失败并撤销其中已经做出的修改。

以下文件路径均相对于 `test/`。运行命令、随机轮数、失败重放和取整误差额度见 [不变量测试说明](README.md)，协议规则编号见 [架构文档](../../../docs/ARCHITECTURE.md)。测试函数或模型限制改变时，应同步更新本文。

## `invariant/AccountingInvariants.t.sol`（3 个不变量）

默认两种 Token 都是 18 位精度。给用户计算份额价格时，只算 Vault 直接持有的资产和当前使用的仓位；核对真实资金流时，还会算上未启用 V2 适配器收到的 LP 捐赠。这样，日后启用 V2、把捐赠计入份额价格时，就不会误以为又赚到了一笔钱。

- `invariant_shareSupplyAndPermanentLock`：把 Vault 自己持有的份额与五个被跟踪账户的份额相加，必须等于总供应量；总供应量也必须等于初始份额加累计新增份额、减累计销毁份额。Vault 自持份额和总供应量不能低于初始锁定量，初始化标志不能丢失。用户可以自愿把额外份额转给 Vault，所以自持份额允许高于初始锁定量。
- `invariant_assetsAndFeesMatchIndependentProtocolAccounting`：直接从真实 V2 Pair、V3 Pool 和仓位管理器重算资产，再与 `totalAssets()`、Vault 快照逐项比较，金额必须精确相等。还要逐个核对三个适配器的本金、待领手续费、资产总量和流动性单位；不拿适配器自己的 `snapshot()` 当参考答案。
- `invariant_cumulativeTokenCashFlowsAreConserved`：分别核对两种 Token 的实际总资产与独立账本。实际总资产包含尚未启用的 V2 LP 捐赠权益；账本累计记录初始化、存款、赎回、捐赠、手续费收入和换币。差额只能来自取整，并且不能超过按实际操作累加的原始单位误差额度。

## `invariant/AccountingMixedDecimals.t.sol`（0 个直接定义，继承 3 个不变量）

`AccountingMixedDecimalsInvariantsTest` 继承 `AccountingInvariantsTest`，只通过 `_tokenDecimals()` 把 token0 改为 6 位、token1 保持 18 位，再执行上述三个会计不变量；没有新增 `invariant_*` 函数。

- 检查两种 Token 精度不同时，份额新增和销毁、永久锁定、协议资产重算和累计资金流仍正确，尤其不能把份额精度误当成 token0 精度。
- 池初始价格仍按原始单位 1:1 设置，策略观察 Tick 为零。因此这里只覆盖该价格条件下的 6/18 位会计检查，不代表任意市场价格或四种精度组合的随机操作序列都已验证。四种精度组合的固定存赎流程见 [集成测试函数目录](../../integration/docs/INTEGRATION_TEST_REVIEW.md)。

## `invariant/VaultInvariants.t.sol`（4 个不变量）

- `invariant_singleActivePositionAndNormalizedPlan`：独立重算历史计划哈希，并核对市场状态应对应哪个池。历史计划版本不能高于当前版本；不在 IDLE 时，当前仓位必须符合历史目标且流动性非零。未使用的 V3 适配器必须没有 NFT、流动性和待领费用；使用中的 V3 NFT 必须归正确的适配器所有，区间及 Tick 间距正确。V2、IDLE 计划的 Tick 应为零，IDLE 资产只能是 Vault 直接持币。未使用的 V2 适配器可以收到外部 LP 捐赠，这是允许的例外。
- `invariant_versionAndHistoricalPlanFollowOnlySuccessfulTransitions`：Handler 自己记录预期版本、完整历史计划摘要和上次迁移时间，再与合约比较。只有成功改变仓位结构的操作才提交新历史；紧急退出会增加版本使旧计划失效，但保留历史计划。普通转账等非结构操作、预期失败和已经 IDLE 时的重复退出，都不能误改历史。
- `invariant_noResidualCustodyOrTemporaryAllowances`：每次操作后，Vault 给三个适配器、适配器给仓位管理器、换币执行器给 Router 的两种 Token 临时授权都应为零；适配器和执行器不应残留底层 Token，Control 也不应持有资产。本模型不直接向这些中间组件捐 Token，所以这里只检查从零余额开始能否正确清理。
- `invariant_bindingsAndAuthorityRemainSeparated`：检查 Token 顺序、Vault 与 Control/执行器的绑定、独立换币池和参考价格池、Router、三个适配器、V3 Tick 间距缓存一直正确，并与官方 Factory 登记一致。根管理员仍是指定账户，且没有自动获得业务角色；五个被跟踪用户都没有根角色。本模型不随机测试根管理员的延迟交接。

## `invariant/HandlerReachability.t.sol`（3 个确定性测试）

这里使用固定操作顺序，确认 Handler 确实能执行重要的成功和拒绝路径。随机短序列不一定能碰到所有路径，Foundry 的调用次数也不等于成功次数。

- `test_handlerReachesAllVenuesFeesDonationsAndRedemptionModes`：按固定顺序完成多用户存款、真实手续费增长、最低到账量过高导致失败、无授权代赎失败、份额授权及直接/授权转账、向 Vault 转入额外锁定份额、本人/有限授权/无限授权赎回，以及 Token 和 LP 捐赠。再依次经过低费率 V3、高费率 V3、V2、IDLE，并按相反顺序返回。检查四种资产位置都到过，存款、赎回和费用操作有成功记录，至少核对两次预期拒绝，收尾前后资金账本都能对上。
- `test_handlerExecutesBothRealRouterDirections`：等冷却期结束后，分别完成一次 token0 换 token1、token1 换 token0 的真实 Router 换币迁移。检查两个方向的成功计数各为 1，收尾前后累计资金流正确。
- `test_handlerChecksFaultsControlsRevocationAndEmergencyLiveness`：遍历八种暂停组合，检查三个受控入口和赎回。再逐个触发冷却未结束、截止时间已过、计划哈希错误、预言机不健康、适配器禁用、Guardian 试图放宽控制、普通用户或根管理员越权，以及 Keeper 撤权后的拒绝。最后让禁用、暂停和预言机故障同时存在，检查仍能代赎和紧急退出，重复退出不增加版本；恢复控制后按历史市场状态迁入高费率 V3。总计至少核对 19 次预期拒绝，并完成收尾账本检查。

## `invariant/handlers/VaultHandler.sol`（17 类随机操作，非独立测试）

只把下列操作交给 Foundry 随机调用。选择器数组有 18 项，因为 `advanceTime()` 放了两次，让时间推进更容易被选中；不同操作函数仍只有 17 个。测试先判断前提是否满足，不满足则记录跳过；满足后实际调用若意外失败，`fail_on_revert = true` 会使测试报错。

- `deposit()`：先独立按仓位本金比例算两种 Token 实际应存多少，再按存款前净值和总份额算应发多少份额。检查实际扣款、份额增加、手续费已领完及最终投入池子的资产比例，并记录流入和新增份额。预言机、暂停、适配器启用、本金或闲置比例不满足存款要求时跳过。
- `redeem()`：选择有份额的用户、赎回量和收款人，分别尝试本人赎回、有限授权代赎或无限授权代赎。检查授权扣减，并由 `_redeem()` 精确核对协议退出量、领取费用后的闲置资产分配、实际到账和份额销毁。
- `transferShares()`：直接转让份额或通过授权转让，接收人可以是五个账户之一，也可以是 Vault。检查双方余额、有限授权用完后为零、总供应量不变；转给自己时单独核对。
- `approveShares()`：让一个被跟踪持有人给另一个被跟踪账户设置份额授权，检查授权金额准确，历史计划不变。
- `donateTokens()`：在限定金额范围内，把两种 Token 直接转给 Vault。记录捐赠流入，检查不增发份额、不改变历史计划。
- `donateLp()`：把 Handler 真正持有的 V2 LP 捐给适配器，按捐赠前后独立计算的权益差记账。V2 未启用时，用户定价总资产必须完全不变；LP 用完则跳过。
- `accrueFees()`：不在 IDLE 时产生真实收益。V3 调用官方 `flash(0,0)` 并在回调中捐 Token，使协议费用记录增长；V2 通过真实转账和 `sync()` 增加池储备。按独立计算的权益变化记录收入，不直接改协议存储。这里只验证收益记账，不模拟常规交易造成的价格变化。
- `setMarket()`：指定预言机快照中的价格偏离程度和健康标志；不改变真实仓位池价格，也不提交新的历史计划。
- `advanceTime()`：把测试时间推进 0 至 180 秒，以便覆盖冷却期结束前后。单独推进时间不能改变计划或上次迁移时间。
- `setControls()`：Manager 可以设置三个暂停开关和适配器启停；Guardian 只能增加暂停、禁用适配器。操作后检查暂停状态正确、历史计划不变。
- `rebalance()`：冷却期结束、预言机健康、入口未暂停、目标适配器启用时，按独立状态切换表核对目标和计划。这里只执行不需换币、且切换到另一个 Venue 的普通迁移；记录版本和历史，并检查最终投入比例。不覆盖同一个 V3 池内的区间重建。
- `rebalanceWithSwap()`：选择相邻且非 IDLE 的目标状态，先捐入一种 Token 造成明确的比例不平衡，再由 Keeper 通过真实 Router 换币。直接从独立换币池余额核对输入、输出，检查协议最低到账量、执行器原有余额未变、最终净值损失未超限、投入比例达标，并记录预期历史；两个方向都可选择。
- `emergencyExit()`：由 Manager 或 Guardian 把仓位退出到 IDLE。检查三个入口全部暂停，历史计划和上次迁移时间保留；从非 IDLE 退出时预期版本加一，已经 IDLE 时不增加。
- `exerciseFailure()`：满足对应前提时，分别触发七种预期失败：赎回最低到账量过高、代赎无授权、截止时间已过、计划哈希错误、预言机不健康、冷却未结束、当前适配器禁用。检查确实失败、错误类型正确、选定状态不变，而不是把任何失败都算通过。
- `unauthorized()`：让普通用户或只有根角色的管理员尝试紧急退出、换币迁移、暂停管理、适配器启用和初始化，检查因缺少对应权限被拒绝。再撤销 Keeper 角色，确认立即不能执行，随后恢复角色。失败的资产调用不应改变被跟踪状态。
- `guardianCannotRelax()`：Guardian 尝试启用适配器必须失败；已有暂停时，尝试解除全部暂停也必须失败。检查选定状态不变。
- `probeGates()`：保留当前暂停、启用和预言机状态，探测存款及两个迁移入口的检查顺序。两个迁移探针故意提交错误哈希，只观察在哪一步被拒绝，不实际迁移；存款只在已知会被某个条件阻止时探测。

统计项分别记录尝试次数 `attempts`、成功次数 `successes`、跳过次数 `skips`、已核对的预期失败次数 `checkedFailures`，以及两个换币方向的成功数和到过的资产位置。某些操作会先改变测试市场输入、授权或捐赠，再判断后续步骤能否执行；因此“跳过”不一定表示整个 Handler 调用什么都没做。所有已发生变化仍须接受账本和历史检查。

## 收尾、参考算法与失败检查（不计入测试数量）

### `invariant/helpers/VaultInvariantFixture.sol`

- `setUp()`：部署共用的真实协议环境，在低费率 V3 初始化，再创建 Handler，转入已有真实 LP 供后续捐赠。只注册明确列出的随机操作，排除环境合约作为随机调用者，避免意外调用仅供收尾的入口。
- `_assertGhostAccounting()`：分别计算两种 Token 的独立参考资产与累计账本之差，绝对值不能超过当前取整误差额度；不会因为随便多了一次外部调用就增加额度。
- `afterInvariant()`：每条随机序列结束后调用 `finish()`，再检查账本正确、已回到 IDLE、剩余总份额等于 Vault 自持份额且不低于初始锁定量、初始化标志保留、两个 V3 仓位 NFT 标识均为零。

### `invariant/handlers/VaultHandler.sol`

- `finish()`：只允许创建 Handler 的测试环境调用。不修复当前预言机、暂停或适配器状态，直接由 Guardian 紧急退出到 IDLE，再让五个账户赎回全部份额。它验证当前故障和控制组合下仍能管理退出、用户仍能赎回；不会取回用户自愿转给 Vault 的额外份额，也不证明 Guardian 永久失联时仍可恢复。
- `assertHistory()`：把合约中的版本、上次迁移时间、历史市场状态和完整计划摘要，与测试独立记录的预期值逐项比较。
- `_redeem()`：先按赎回前总份额，向下取整应退出的 V2 LP 或 V3 liquidity，再计算能取回多少 Token，以及领取费用后应分给用户多少 Vault 直接持币。精确核对两种 Token 的实际到账、用户余额和销毁份额，并记录真实流出。
- `_failure()` / `stateDigest()`：使用低级调用检查操作确实回滚、错误类型匹配，且选定状态摘要不变。摘要包括资产、仓位、历史、份额、授权、相关池和中间组件；没有检查全部存储，也没有逐一检查所有错误参数。

### `invariant/helpers/VaultReference.sol`

- `v2()`：读取适配器实际持有的 LP、Pair 储备和 LP 总供应量，独立向下取整计算对应的两种 Token。
- `v3()`：读取真实 NFT 的区间、liquidity、已记入可领取金额的费用及上次费用增长记录；再读取真实池价格、Tick、边界和全局费用增长，按价格所在区间独立计算本金和新产生但尚未记入可领取金额的费用。
- `amounts()`：按仓位边界限制用于计算的价格，再按官方退出规则计算两种 Token 数量；token0 分两步向下取整，token1 一步向下取整。

## 覆盖限制

- Vault、Control、适配器、换币执行器、Oracle 报价函数，以及官方 AMM（自动做市协议）、Router、仓位管理器均真实执行。但随机模型控制 Oracle `snapshot()`，观察 Tick 固定为零，仓位池价格固定。独立换币池上的真实交易可以改变那个池的价格，不会自动变成策略 TWAP 的自然变化。
- 参考模型不以适配器 `snapshot()` 为答案，但与生产共用 `PriceMath.sqrtRatioAtTick`，即把 Tick 转成平方根价格的基础函数；双方如果在此函数中有同一个错误，本套件无法独立排除。
- 默认会计和状态测试都是 18/18 位精度；混合精度只重复 6/18 位的三个会计不变量。13 个执行实例不代表所有精度下的全部规则都验证过。
- 份额定价、实际扣款和到账、授权、协议状态使用精确比较；只有累计资产账本允许明确的原始单位取整误差。具体额度见 [不变量测试说明](README.md#会计模型与舍入预算)，不能理解为生产合约可以任意损耗资产。
- 本随机模型不验证真实 TWAP 变化、负 Tick、价格越界、同池区间重建、无常损失、恶意 Token/Router/适配器、重入、管理员延迟交接或主网分叉行为；这些需结合单元、集成和专项测试判断。
